# FingerPrintGetterPlus

**English** | [简体中文](README.zh-CN.md)

[![CI](https://github.com/kiwi0719/FingerPrintGetterPlus/actions/workflows/ci.yml/badge.svg)](https://github.com/kiwi0719/FingerPrintGetterPlus/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)

Browser and device fingerprint collection for anti-fraud. Runs entirely within Cloudflare's free tier.

- **Backend**: Cloudflare Worker (edge compute, no cold starts)
- **Storage**: Cloudflare D1 (SQLite; free tier covers 5M reads / 100K writes per day)
- **Frontend**: FingerprintJS open-source edition + 70+ custom extra signals
- **Entry points**: a Telegram bot that mints collection links, plus a web admin panel

> ### ⚠️ Scope of use
>
> This project collects personal data that identifies a specific device. **Use it only on services you operate, against visitors who have been informed**, for risk control and fraud prevention.
>
> Do not use it to track or surveil people without authorization, do not inject it into third-party pages, and do not collect without disclosure. Comply with your local privacy law (GDPR, PIPL, etc.). The tool does not judge the legality of your use — **operators bear full responsibility**.
>

## Core concepts

| Field | Meaning | Stability |
|---|---|---|
| `visitorId` | Browser identity generated by FingerprintJS | Stable per browser; changes across browsers |
| `hw_id` | **Hardware-only** hash: canonical GPU / WebGPU adapter / audio hardware params / physical screen params | Same across browsers **and** networks on one physical machine |
| `os_id` | `hw_id` + system font set + timezone + system language + platform version | Survives a network change; changes on OS reinstall |
| `cross_id` | `os_id` + client IP | Legacy behaviour; changes with the network (kept for compatibility) |
| `bot_score` | Automation / bot suspicion, 0 (human) to 1 (highly suspicious) | Evaluated per collection |
| `session_id` | The token of one collection link; a link can be opened many times | — |

**Which one to query with:**
- Recognise "same person, different browser" → `hw_id` (recommended)
- Recognise "same person, different network *and* browser" → `hw_id`
- Recognise "same machine before and after an OS reinstall" → `hw_id` (pure hardware does not change)
- Match legacy behaviour exactly → `cross_id`

Beyond exact matching, `/api/risk` also does fuzzy matching with **per-field similarity scoring + a font-bitmap Hamming distance**, tolerating 1–2 fields of drift (e.g. only `screen_res` changed because of a new monitor).

## Signals collected

**Hardware**: fine-grained GPU (WebGL vendor/renderer/extensions/bit depth/viewport), WebGPU adapter info, AudioContext fingerprint + sampleRate/baseLatency, physical screen params, presence of 6 sensor API classes, battery status, storage quota

**System**: 60+ font probes (full CJK coverage), timezone, Intl locale/numberingSystem/calendar, language chain, keyboard-layout map (high entropy), the full UA-CH high-entropy set (architecture/bitness/model/platformVersion/fullVersionList)

**Browser capabilities**: video codecs (H.264/HEVC/AV1/VP8/VP9), audio codecs (AAC/AC-3/MP3/Opus/FLAC), EME/DRM support (Widevine/PlayReady/FairPlay/ClearKey), Speech Synthesis voice list, presence of 17 APIs

**Rendering**: Canvas 2D hash, Canvas emoji hash, Text Metrics (fontBoundingBox and 10+ other measures), CSS media queries (prefers-* / color-gamut / dynamic-range / hover / pointer / forced-colors and 15 more)

**Network**: WebRTC local/public IP + SDP codecs, Connection API (effectiveType/downlink/rtt)

**Anti-automation**: webdriver / headless multi-signal detection, native-function integrity (whether fetch/canvas/toDataURL have been monkey-patched), clock jitter (minimum `performance.now` step), Error-stack engine identification (V8/SpiderMonkey/JSC), 15+ automation-framework hook probes (Selenium/Puppeteer/Nightmare/PhantomJS)

**Server-side (CF edge enrichment)**: all Sec-CH-* / Sec-Fetch-* / Accept-* headers, Referer, Origin, GPC, DNT, TLS version + cipher suite, HTTP protocol version, TCP RTT, edge node (colo), precise geo (lat/long/postal), ASN organisation, Bot Management score, threat score

## Deploy

### Prerequisites

**1. Node.js 18+ and npm**
```bash
node --version   # >= 18
```

**2. Cloudflare API token**

Go to https://dash.cloudflare.com/profile/api-tokens → Create Token → Custom token, with:
- `Account` → `Workers Scripts` → Edit
- `Account` → `D1` → Edit
- `Account` → `Workers KV Storage` → Edit (needed for Assets)

Save the generated token (shown only once).

**3. Cloudflare Account ID**

Sign in at https://dash.cloudflare.com — it's the segment in `dash.cloudflare.com/<account_id>/...`, or the Account ID in the right-hand sidebar.

**4. Telegram bot token**

In Telegram, search `@BotFather` → `/newbot` → pick a name → receive a token like `123456789:ABC-DEF...`.

### One-command deploy

```bash
git clone https://github.com/kiwi0719/FingerPrintGetterPlus.git
cd FingerPrintGetterPlus

# Pass everything on the command line (most direct)
./deploy.sh \
  --cf-token=<your CF API token> \
  --cf-account=<your CF Account ID> \
  --tg-token=<your Telegram bot token>

# Or short flags
./deploy.sh -t <cf_token> -a <cf_account> -b <tg_token>

# Or just run it and answer interactively (token input is hidden)
./deploy.sh
```

The script:
1. runs `npm install`
2. creates the D1 database (reuses it if it exists) and initialises the schema
3. injects `TELEGRAM_BOT_TOKEN` and `ADMIN_KEY` via the Cloudflare API (as secrets, never committed)
4. deploys the Worker once to obtain its `workers.dev` domain
5. writes `BASE_URL` back and deploys again
6. points the bot webhook at `/tg/webhook`
7. prints the one-click admin URL with `#key=` embedded (macOS opens it in the browser automatically)

Example output:
```
✅ Deploy complete!

🔗 Admin panel (click to open, key embedded):
   https://fingerprint-collector.<your-subdomain>.workers.dev/#key=<random>

🤖 Telegram bot:      https://t.me/<your-bot-username>
🎯 Collection prefix: https://fingerprint-collector.<your-subdomain>.workers.dev/c/<token>

Admin key (save it, keep it secret):
  ADMIN_KEY=xxxxxx
```

### Deploy script flags

| Flag | Short | Default | Meaning |
|---|---|---|---|
| `--cf-token` | `-t` | — | Cloudflare API token (required) |
| `--cf-account` | `-a` | — | Cloudflare Account ID (required) |
| `--tg-token` | `-b` | — | Telegram bot token (required) |
| `--admin-key` | `-k` | random 32-byte hex | Web admin panel / risk API key |
| `--turnstile-secret` | — | (unset) | Turnstile server-side secret; if unset the server-side re-check is skipped, but the widget still renders |
| `--worker` | `-w` | `fingerprint-collector` | Worker name (decides the workers.dev prefix) |
| `--db` | `-d` | `fingerprint-db` | D1 database name |

Environment variables are also honoured (same names): `CLOUDFLARE_API_TOKEN` / `CLOUDFLARE_ACCOUNT_ID` / `TELEGRAM_BOT_TOKEN` / `ADMIN_KEY` / `TURNSTILE_SECRET` / `WORKER_NAME` / `DB_NAME`. Command-line flags take precedence.

> The script tracks applied migrations in a `_migrations` table, so `deploy.sh` is **safe to re-run** (already-applied migrations are skipped). For small code changes, `npx wrangler deploy` on its own is fine too.

Run `./deploy.sh --help` for the built-in help.

## Usage

### Telegram bot

Sending the bot **any message** returns a fresh collection link, with the message text kept as a label:

```
you: /start
bot: https://fingerprint-collector.xxx.workers.dev/c/abc123...

you: order #42, Zhang San
bot: https://fingerprint-collector.xxx.workers.dev/c/def456...
```

Send the link to the target. When their browser opens it, collection finishes in about 1–3 seconds (the page shows "device check complete") and the data lands in D1. **You do not get a notification** — check the admin panel for the details.

The bot also runs a two-way relay: a stranger who messages the bot is asked to open a device-check link first (the page discloses what it collects); once done, their later messages are forwarded to the owner, who can reply through the bot. See [`src/telegram.js`](src/telegram.js).

### Web admin panel

**Entry**: `https://<your-domain>/#key=<ADMIN_KEY>`

The first time you open it with the key, the key is stored in `localStorage`; later visits to the root domain (without `#key=`) log in automatically. The `#key=` fragment is never sent to the server (so it stays out of access logs and `Referer`), and it is stripped from the address bar immediately, so a refresh, screenshot or shared URL does not leak it.

**Panel features:**
- Top stat cards: total sessions, pending count, total fingerprints, unique browsers, **unique devices** (by `cross_id`), unique IPs, high-risk bot count
- Detail table: time / label / visitorId / cross_id / IP / country / risk level / expand for the full signal JSON
- Clicking a `cross_id` in the table opens that device's correlation analysis (hit count / related IPs / risk flags)
- An "Export CSV" button downloads the latest 1000 rows

### HTTP API

For your own backend to call. Every endpoint needs the `x-admin-key` header. A `?key=` query parameter is no longer accepted (it would end up in access logs).

```bash
KEY=<your ADMIN_KEY>
BASE=https://<your workers.dev domain>

# Summary stats (totals, unique device count, top 10 devices, etc.)
curl -H "x-admin-key: $KEY" "$BASE/api/stats"

# All fingerprints (paginated, includes full signal JSON)
curl -H "x-admin-key: $KEY" "$BASE/api/all?limit=100&offset=0"

# Export CSV
curl -H "x-admin-key: $KEY" "$BASE/api/all?format=csv&limit=1000" > all.csv

# Session list (lightweight, no signals)
curl -H "x-admin-key: $KEY" "$BASE/api/sessions?limit=50&status=collected"

# All reports for one session (a link opened in several browsers yields several rows)
curl -H "x-admin-key: $KEY" "$BASE/api/session/<token>"

# Risk lookup (five dimensions, pick one)
curl -H "x-admin-key: $KEY" "$BASE/api/risk?hw=<hw_id>"          # recommended: same machine across browsers + networks
curl -H "x-admin-key: $KEY" "$BASE/api/risk?os=<os_id>"          # hardware + system match (across networks)
curl -H "x-admin-key: $KEY" "$BASE/api/risk?cross=<cross_id>"    # strict match (includes IP)
curl -H "x-admin-key: $KEY" "$BASE/api/risk?visitorId=<visitorId>"
curl -H "x-admin-key: $KEY" "$BASE/api/risk?ip=1.2.3.4"
```

The lookup returns three buckets:
- `exact` — history that matches the queried identifier exactly
- `same_hw` — same `hw_id` (same physical machine across browsers/networks)
- `similar` — hardware fields + font-bitmap Hamming distance scoring (total ≥ 4/10); each row carries `_match.parts` breaking the score down

plus the correlated session/IP/visitor lists and the **risk flags**.

### Querying D1 directly

For heavier analysis, run SQL against D1:

```bash
export CLOUDFLARE_API_TOKEN=<...>
export CLOUDFLARE_ACCOUNT_ID=<...>

# Latest 50 rows
npx wrangler d1 execute fingerprint-db --remote \
  --command "SELECT * FROM fingerprints ORDER BY created_at DESC LIMIT 50"

# Device aggregation: most-collected devices and the IPs they used
npx wrangler d1 execute fingerprint-db --remote --command "
  SELECT cross_id, COUNT(*) hits, COUNT(DISTINCT session_id) sessions,
         GROUP_CONCAT(DISTINCT ip) ips
  FROM fingerprints
  GROUP BY cross_id ORDER BY hits DESC LIMIT 20"

# Likely bot traffic
npx wrangler d1 execute fingerprint-db --remote --command "
  SELECT * FROM fingerprints WHERE bot_score >= 0.6 ORDER BY created_at DESC"

# Dump everything to local JSON
npx wrangler d1 execute fingerprint-db --remote --json \
  --command "SELECT * FROM fingerprints" > dump.json
```

You can also query it in the Cloudflare dashboard:
`https://dash.cloudflare.com/<account_id>/workers/d1/fingerprint-db` → the Console tab.

## How cross-browser identification works

**`visitorId`** is generated by FingerprintJS from many browser-observable signals (Canvas, font list, userAgent, language, timezone, screen, plugins, etc.). When the same device switches browsers, the userAgent, language and font-rendering details all change, so `visitorId` **differs**.

**The layered IDs (`hw_id` / `os_id` / `cross_id`)** are generated server-side by this project, each from fields of a different stability:

`hw_id` — hardware-only, SHA-256 of:
- canonical GPU (driver version / D3D shader-model tail stripped) + vendor + sorted WebGL extension set + `MAX_TEXTURE_SIZE`
- WebGPU adapter info (vendor/architecture) — a fallback when Safari masks the GPU
- audio fingerprint + `sampleRate` + `baseLatency`
- physical screen resolution + colorDepth

`os_id = SHA-256(hw_id | exact font hash | timezone | UA-CH platform+version | language set)`

`cross_id = SHA-256(os_id | ip)` — matches legacy behaviour.

**Notes:**
- `hardware.cores` and `hardware.memory` are **not hashed** (modern browsers return only a few bucketed values, very low entropy). They are stored in their own columns for scoring only.
- The GPU renderer is normalised by `canonicalGpu()` (see [src/fonts.js](src/fonts.js)) to strip version numbers — otherwise the same machine on a different driver version would not match.
- Besides the exact font hash, fonts are also encoded into a **128-bit bitmap** (`fonts_bitmap`), and `/api/risk` fuzzy-matches with **Hamming distance** — 1–2 font differences no longer break the match.

To verify: open the same collection link in two different browsers on one computer → `visitorId` differs, but `hw_id` / `os_id` / `cross_id` are all identical; switch WiFi and open it again → `cross_id` changes while `hw_id` / `os_id` stay the same.

## Risk flags

The `risk_flags` array returned by the lookup:

| Flag | Meaning |
|---|---|
| `same_device_many_sessions` | One device collected 3+ times → possible account reuse / multi-boxing |
| `device_ip_hopping` | One device used 3+ distinct IPs → frequent VPN/proxy switching |
| `cross_asn_device` | One device used 3+ distinct ASNs → cross-datacenter / cross-carrier proxying |
| `automation_suspected` | A record with bot_score ≥ 0.6 appeared → suspected automation |
| `incognito_seen` | An incognito visit appeared → possible cookie-tracking evasion |

## Maintenance

**Update code**
```bash
git pull
npx wrangler deploy
```
No need to re-run `deploy.sh` (secrets and D1 are untouched).

**Live Worker logs**
```bash
npx wrangler tail
```

**Rotate ADMIN_KEY** (if you suspect a leak)
```bash
NEW_KEY=$(openssl rand -hex 32)
echo -n "$NEW_KEY" | npx wrangler secret put ADMIN_KEY
echo "new key: $NEW_KEY"
# Then reopen /#key=<new key>; localStorage updates.
```

**Rotate the bot token** (after BotFather `/revoke`)
```bash
echo -n "<new token>" | npx wrangler secret put TELEGRAM_BOT_TOKEN
curl "https://api.telegram.org/bot<new token>/setWebhook?url=<BASE_URL>/tg/webhook"
```

**Wipe the database** (use with care)
```bash
npx wrangler d1 execute fingerprint-db --remote \
  --command "DELETE FROM fingerprints; DELETE FROM sessions;"
```

**Tear down the deployment**
```bash
npx wrangler delete                                  # remove the Worker
npx wrangler d1 delete fingerprint-db                # remove D1 (data is unrecoverable)
```

## Development and testing

```bash
npm install
cp wrangler.toml.example wrangler.toml   # fill in your own D1 database_id
npm run db:migrate:local
npm run dev                              # local Worker + local D1
```

```bash
npm test                                 # Node's built-in runner, no extra dependencies
```

Tests cover the pure functions in `src/fonts.js` and `src/risk.js` (font bitmap, Hamming distance, GPU canonicalisation, similarity scoring, risk flags). Worker-runtime code is not yet tested.

> **Be careful editing `CANONICAL_FONTS`**: its order must match the probe order in `public/extra-signals.js` exactly, and you may only append to the end. Inserting or reordering invalidates **every historical bitmap**.
